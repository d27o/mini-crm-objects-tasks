# Решения и допущения

Там, где ТЗ не даёт однозначного ответа, решил так:

## Роли и доступ
- **Роль хранится в таблице `profiles`.** Новый пользователь всегда исполнитель; постановщика
  назначает администратор в Supabase. Через интерфейс роли не меняются (не было в ТЗ).
- **Исполнитель видит на объекте только свои задачи**, а не все задачи объекта. ТЗ: «видит только
  свои задачи».
- **Все сотрудники видят имена и email друг друга.** Иначе исполнитель не увидит, кто автор задачи и
  кто вернул её на доработку. Считаю это допустимым для внутренней системы.
- **Постановщики равноправны:** любой постановщик может принимать и править задачи другого.

## Задачи
- **Исполнитель обязателен при создании** и может быть только пользователем с ролью «исполнитель».
  Задача без исполнителя никуда не может двигаться (все переходы из «Новой» делает исполнитель).
- **Постановщик может редактировать задачу в любом статусе**, включая смену исполнителя и
  объекта. Например, если исполнитель заболел. Статус при этом не меняется; новый исполнитель
  продолжает с того же места. Смена исполнителя в историю не пишется: ТЗ требует историю статусов.
- **Исполнитель не редактирует поля задачи**, только меняет статус.
- **«Принята» — финальный статус.** Других переходов в ТЗ нет, поэтому переоткрыть задачу нельзя.
- **Комментарий необязателен при остальных переходах**, но в функции поддержан для всех.
  В интерфейсе поле комментария показывается только при возврате на доработку.
- **Удаление задачи удаляет её историю.** Через API историю удалить нельзя, но если постановщик
  удаляет саму задачу, история без задачи смысла не имеет. Альтернатива — мягкое удаление
  (архив); не стал делать ради объёма.
- **Объект с задачами удалить нельзя**: база вернёт ошибку, интерфейс подскажет удалить или
  перенести задачи. Так случайно не потерять задачи и историю.

## Технические
- **Статус меняется только через функцию `change_task_status()`.** Прямой `UPDATE` колонки `status`
  запрещён правами на уровне колонок, плюс триггер-страховка.
- **Одновременные действия:** функция блокирует строку задачи на время смены статуса, поэтому
  два одновременных нажатия не создадут две записи истории.
- **Оформление без UI-библиотеки**: простой CSS, чтобы не тянуть зависимость ради форм и таблиц.
- **Список задач без пагинации**: для тестового объёма не нужно.

## Что не успел или не делал
- Нет экрана управления пользователями: они создаются в Supabase или скриптом `npm run seed`.
- Нет обновления в реальном времени: чтобы увидеть чужие изменения, нужно обновить страницу.
- Нет фронтенд-тестов; покрыты тестами правила в базе — там, где проходит граница безопасности.
- Нет поиска и фильтров на списке объектов (фильтр по статусу есть только в «Моих задачах»).
