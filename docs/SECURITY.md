# Как защищены данные (техническая версия)

Фронтенд ходит в Supabase с публичным `anon`-ключом и JWT пользователя. Поэтому любой вошедший
пользователь может слать в API произвольные запросы, и всё должно проверяться в базе.

Защита в три слоя:

| Слой | Что делает |
|---|---|
| **GRANT** (права на таблицы и колонки) | Убраны все права по умолчанию у `anon` и `authenticated`. `task_history`: только `SELECT`. `profiles`: только `SELECT`. `tasks`: `INSERT`/`UPDATE` только колонок `title, description, site_id, assignee_id`, поэтому изменить `status`, `author_id`, `created_at` напрямую невозможно в принципе. |
| **RLS** (какие строки) | Постановщик видит и меняет всё. Исполнитель видит только задачи, где он исполнитель, объекты, где у него есть задачи, и историю своих задач. Создавать, менять и удалять объекты и задачи может только постановщик. |
| **Триггеры и функция** | `change_task_status()` (security definer) — единственный способ сменить статус: проверяет, что пользователь видит задачу, что переход разрешён таблицей переходов и роль подходит, что при возврате на доработку есть комментарий. Затем сама пишет запись в историю. При создании задачи триггер принудительно ставит `status = new`, `author_id = auth.uid()` и пишет первую запись истории. |

Роль хранится в `profiles.role`. Пользователь не может её изменить (нет права `UPDATE`),
новый пользователь всегда получает роль `executor`.

Проверка — `supabase/tests/01_access_test.sql`: 35 сценариев, включая прямые запросы в обход
интерфейса (сменить статус через UPDATE, подделать историю, взять чужую задачу, принять задачу
исполнителем, обратиться анонимно).
